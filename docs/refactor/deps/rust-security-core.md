## 1. Shared-trait groups (must move together)

- **digest 0.11 group**: sha2 0.11, hmac 0.13, hkdf 0.13 (hkdf 0.13 requires hmac 0.13 which requires digest 0.11), ed25519-dalek 3 (uses sha2 0.11), argon2 0.6 (blake2 0.11). Move sha2+hmac+hkdf as ONE step (cryptography, proto, core all use sha2 0.10 alongside hkdf/hmac; mixing 0.10 Digest types with hkdf 0.13 will not type-check).
- **rand_core 0.10 group**: rand 0.10, ed25519-dalek 3, x25519-dalek 3 (curve25519-dalek 5), and `signature` 3 / `ed25519` 3. `StaticSecret::random_from_rng` and `SigningKey::generate` need a rand_core 0.10 CryptoRng. rand 0.8's OsRng implements rand_core 0.6 and will NOT satisfy it. So x25519-dalek 3 + rand 0.10 must be taken together in `cryptography` (ecies.rs:19).
- **aead 0.6/cipher 0.5 group**: aes-gcm 0.11 (aead 0.6, aes 0.9, cipher 0.5). Independent of digest/rand_core versions (changelog mentions no rand_core change), so it can go on its own, but both `cryptography`, `proto` and `core` (+ `group-sim`) use aes-gcm; unify in one commit. (iroh's noq-proto pulls aes-gcm 0.10 too, so a second copy stays regardless.)
- bip39 3.0 and base64 0.23 are independent (bip39 3.0: OS RNG for generation, `rand` feature optional; we call neither `generate*` nor enable `rand`).
- redb, uniffi, bincode: independent of the above.
- All new RustCrypto releases: edition 2024, **MSRV 1.85** (sha2 0.11.1 -> 1.88; redb 4.3 -> 1.90; uniffi 0.31+ -> 1.87; rand 0.10 -> 1.85). Local rustc 1.92 is fine; check the CI/NDK Rust toolchain used by cargo-ndk is >= 1.90.

### 2.1 bincode 1.3.3 -> 3.0.0  (CRITICAL: skip)
- (1) crates.io 3.0.0 (2025-12-16) is a **tombstone**: README + a lib.rs that triggers a compile error; docs.rs build fails; maintainers ceased development after a doxxing/harassment incident; README points to wincode (bincode-compatible), postcard, rkyv. Last functional line is 2.0.1 (2025-03-10); 1.3.3 (2021-04-10) is declared "complete". Sources: https://docs.rs/bincode/3.0.0/bincode/ , https://crates.io/api/v1/crates/bincode/versions .
- (2) RUSTSEC-2025-0141: INFO / unmaintained, no patched version, no vulnerability (https://rustsec.org/advisories/RUSTSEC-2025-0141.html). `cargo audit` will print it as a warning only.
- (3) bincode is used by identity (keystore.rs:40,44) and core (≈70 sites). Categories:
  - **Wire frames** (tinline/chat/3, self/3, group/2): core/src/chat/wire.rs:91,108; sync/frames.rs:32,48; group/wire.rs:123,139 (u32 BE length + bincode of enums). Tested against a raw peer in tests/grant_characterization.rs:414,427.
  - **Signed bodies**: group/record.rs:154,162,170-177,195-196,230-239,265-276 (`SignedRecord/Invite/HostAddr`: body = bincode(self), sig over body; verification **re-serialises and requires byte equality** (record.rs:177, 239, 276; mail.rs:88)), group/mail.rs:74-118.
  - **Persisted rows**: group/code.rs:293,395,460; group/requests.rs:379,392 (tuple `(u64, Vec<u8>)`); group/store.rs:270,274; group/api.rs:858; group/engine.rs:1440,1860; search/index.rs:260,507,740 (Manifest); identity keystore blob.
  - **Shared links**: group/invitations.rs:123,130 (`Letter` base64url-bincode in invite links), invitations.rs:445,522,610,653,689; own.rs:37,50 (`InviteToken`).
- (4) Data/wire risk: bincode 1 `serialize` = little-endian, fixed-int, no length limit, trailing bytes allowed on deserialize. bincode 2.x defaults differ (varint); only `bincode::config::legacy()` + `serde` feature (`bincode::serde::encode_to_vec/decode_from_slice`) reproduces 1.x bytes, and it errors on unknown trailing semantics differently. Any divergence breaks signature verification of existing signed records (re-serialise-equals check), old invite links, persisted rows, and cross-version peers. There is no upgrade benefit worth that risk right now.
- (5) Recommendation: **keep bincode 1.3.3** (pin `=1.3.3`-compatible "1"); add to deny/audit ignore with a comment. If/when migrating, do it as a separate project: introduce a thin `wirecodec` module with `ser()/de()` used at all 70 sites, choose wincode or bincode 2 legacy config, and gate with golden-bytes tests: serialize representative values of every type in the lists above with bincode 1 today, check the hex into the repo, assert the new codec emits identical bytes AND decodes them, plus fuzz round-trip (new->old and old->new) against the frozen 1.3.3 as a dev-dependency. Effort L (broad, high blast radius), not urgent. Possibly worth doing the golden-bytes capture now (S) so it exists when needed.

### 2.2 redb 2.6.4 -> 4.4.0  (holds ALL user data)
- (1) Changes (https://github.com/cberner/redb/blob/master/CHANGELOG.md):
  - 3.0.0: **removes support for file format v2**; v3 format; min file size 2.5 MiB -> ~50 KiB; variable-width tuple encoding changed (we use only `&str`/`&[u8]`, so unaffected); API: `StorageBackend::read` signature, `set_durability` returns Result, `Durability::Paranoid` removed, `begin_read()`/`cache_stats()` moved to `ReadableDatabase` trait (must `use redb::ReadableDatabase`), `ReadOnlyDatabase`, `Builder::open_read_only`.
  - 4.0.0: `AccessGuardMut` Drop semantics, `Legacy` removed. 4.1-4.4: compaction/savepoint error changes (4.2: `compact()` returns Persistent/EphemeralSavepointExists; 4.4: `compact()` returns `CompactionError::TransactionInProgress` instead of blocking if a write txn is held), 3.1.3 fixes data loss when `get_mut` guard dropped after commit. MSRV of 4.3.0 = **1.90**, edition 2024 (Cargo.toml in registry).
  - Upgrade path (documented): v2 -> v3 via `Database::upgrade()` introduced in **2.6** (we are on 2.6.4, so it exists: redb-2.6.4/src/db.rs:459; `&mut self`, returns Ok(true) if upgraded, errors if savepoints/read txns exist, uses two-phase commits).
- (2) Advisories: none in RustSec for redb. Not a security driver.
- (3) Call sites that break: storage/src/store.rs: `begin_read()` (needs `ReadableDatabase` import) at the read paths; `table.range(prefix..)` (should still infer for `&str`; verify), `txn.stats()` and `db.compact()` (store.rs:108,122) keep signatures but semantics of compact error 4.4 above (we hold the write lock so no txn should be in flight; map the new error); error.rs:6-16 `#[from]` types: check names still exist (`CompactionError`, `DatabaseError`, `StorageError`, `TableError`, `TransactionError`, `CommitError` all still exported in 4.3 per src/error.rs). In-memory backend `Builder::create_with_backend(InMemoryBackend::new())` unchanged. Otherwise tiny: one file.
- (4) **DATA RISK (the main one)**: redb 2.6.4 `Database::create` defaults to file format **v2** (`default_to_file_format_v3: false`, db.rs:1137; `Builder::create_with_file_format_v3` is opt-in). So every account.redb / chat.redb / group.redb / search.redb on user devices today is v2. redb 4.3's header check returns `DatabaseError::UpgradeRequired(2)` for v1/v2 files (4.3.0 src/tree_store/page_store/header.rs:504-506) - i.e. a plain dependency bump would make the app unable to open existing data (looks like data loss; sealed stores would surface as an open error). iroh-blobs' redb 4 is irrelevant (separate blob DB it created itself; unaffected).
  - Values are AES-GCM sealed bytes by `storage::Sealed` (sealed.rs), keys are `&str` paths; so there is no redb-level type/encoding exposure (no tuples, no Option, no niche) - only the container file format changes.
  - Required shim: keep redb 2.6.4 as a renamed dependency (`redb2 = { package = "redb", version = "=2.6.4" }`, already in lock) used ONLY by a `migrate_v2_to_v3(path)` that: (a) copies the file to `<name>.v2.bak` (check free space; keep until next successful open), (b) `redb2::Database::open(path)?.upgrade()?` (needs `let mut db`), drop, (c) then open with redb 4. Store::open: try redb 4 -> on `DatabaseError::UpgradeRequired(_)` run the shim and retry once. Do this before opening any account (rekey.rs and accounts.rs also open files: accounts.rs:5-6,63; rekey.rs migrations use Store, so central in Store::open is enough). Alternative if a dual-version dependency is unwanted: first ship a release on redb 2.6.4 that calls `upgrade()` on open (also v3-creates new files), wait one release cycle, then bump to 4. That is cleaner but delays; the shim handles users who skip releases, so prefer the shim (or both).
  - After v3 the file can NOT be opened by the old (2.6.4) build; a downgrade of the app after upgrade means data unreadable -> keep the .bak for one successful session/launch and tell release notes.
  - Android: files are under the app data dir; the upgrade rewrites pages in place (2 two-phase commits); crash mid-upgrade -> redb repair; backup covers the rest. Also check `Store::compact` still behaves (4.4 changed lock-wait).
- (5) Effort M-L (code small; migration + tests are the work). Recommendation: **upgrade with the shim + tests; do it independent of crypto upgrades; ship in a release by itself**, or at minimum behind the shim. Acceptance tests:
  1. Binary fixture: generate (with a redb2-based test helper or checked-in file made by the current release build) a v2 `.redb` containing: several thousand keys under realistic prefixes (shard/…, hosts/…, m, etc.), large values (>1 MiB), deleted keys, and a sealed account.redb; test opens it through the NEW `Store::open`, asserts every key/value byte-identical, `scan`/`scan_prefix` ordering identical, file now reports v3 (open with redb 4 directly succeeds), `.bak` exists and equals the original hash.
  2. Same through `Sealed` + real data key: decrypt every record (proves no value corruption).
  3. Crash-injection: kill the process (or truncate/fault a backend copy) between backup and upgrade and during upgrade; reopen must yield the full data (old file via .bak restore or redb repair).
  4. Idempotence: opening an already-v3 file does not re-run the shim and does not touch the .bak.
  5. Year-scale: run `year-bench` style DB (docs/scale-year.md) through migration; compare `Store::usage()` and timing; run on an Android emulator with a pre-populated account (rekey, chat_open flows in docs/vault.md).
  6. `compact()` after migration returns without `TransactionInProgress`.

## 3. Proposed upgrade order (each step its own commit/branch, all via scripts/buildlock.py; per AGENTS.md no staging by agents without authorisation)

0. **Freeze behavior first (no dependency change)**: add golden-vector tests on CURRENT versions: BIP-39 mnemonic -> seed -> keys -> DID; Argon2id vault/keystore KEK; HKDF contexts; AES-GCM frozen blobs (Sealed value, vault wrapped_dek, keystore bytes, link ticket, chunked blob); Ed25519/X25519 RFC vectors and old-build signatures/ECIES ciphertext; golden bincode bytes for every wire/signed/persisted type; a checked-in (or test-generated through redb2 `Builder::create_with_file_format_v3(false)`) v2 redb fixture. Each later step must keep these passing unchanged.
1. **base64 0.23** (trivial, independent).
2. **redb 4 + v2->v3 shim** (independent; highest user-data risk; ship alone, with .bak, and monitor). Alternatively precede with a release on 2.6.4 that calls `upgrade()`.
3. **uniffi 0.32.2** (independent; Kotlin/device validation; includes re-check of `Bytes` converter and callbacks). Can run in parallel with step 2 on a different branch since they touch disjoint files (storage vs core ffi), but ship separately.
4. **RNG helper refactor on rand 0.8** (pure refactor: all OsRng/fill_bytes/random through `cryptography::rng`), then
5. **Crypto group in one PR**: rand 0.10 (or getrandom) + sha2 0.11 + hmac 0.13 + hkdf 0.13 + ed25519-dalek 3 + x25519-dalek 3 + aes-gcm 0.11 + argon2 0.6 + bip39 3.
