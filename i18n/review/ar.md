# Arabic (ar) review

Language: ar · File: `i18n/tm/ar.toml` (feeds `i18n/ar/{android,ios,desktop}.toml`) · Entries: 2053 · ok 1969 · fixed 84 · native 12 items (term and tone rulings over about 150 entries, left as they are) · restructure 8 new items
Reviewer: `i18n-review-ar` (2026-10-25), independent of the translator. Checked against `i18n/VALIDATION.md`, `i18n/glossary/README.md`, `i18n/glossary/ar.md` and `docs/design/VOICE.md`.
Confidence after review: **medium-high** for meaning and grammar, **medium** for display (bidi needs the code-side isolation below) · Biggest issues: bidi in strings that start with a name slot or a Latin word, grammar slips in short labels (bare accusatives, plural agreement in non-plural strings), and a few word choices that change the meaning («إعادة التشغيل» = reboot, «إشعارات القراءة» clashes with notifications, «انتحال هويتك»).

## Verdict

**Ship as a draft.** The translation is good Modern Standard Arabic and reads like a modern phone app, not like a machine translation. It follows the glossary throughout (السر الجذري, كلمات الاسترداد, عبارة المرور, خطك مفتوح, ربط/إلغاء الربط, حظر, مضيف, خادم ترحيل, مشفّر تمامًا بين الطرفين). The gender-neutral strategy holds: buttons are masdars, “you” text uses `يمكنك` + masdar, passives or «لديك», and contacts mostly appear in nouns («مكالمة من {name}», «طلب إضافة من {name}»). There are no «قم بـ», «الرجاء» or exclamation marks. Punctuation is Arabic (، ؛ ؟ « »). All six plural forms are present and correct in every plural entry (dual, 3–10 genitive plural, 11–99 accusative singular, 100+ genitive singular). I found one adjective-agreement slip, now fixed.

What stops it from being final:
1. **Bidi.** 128 entries start with a placeholder or a Latin word. With a Latin name, Android Compose, SwiftUI and cosmic-text all pick the paragraph direction from the first strong character, so the line is laid out left to right and aligned to the wrong side. That has to be fixed in code (section “Bidi”); translations can't fix it.
2. **Fragments.** Arabic can't fill the “You/Someone/them” slots and the glued pieces already listed in `i18n/RESTRUCTURE.md` §1–§9e. I gave the best translation for the most common slot.
3. **The native-speaker items** below (mainly «إبلاغ» for flag and the plural «رمزهم» for one person).

Checks run after the edits: `python3 scripts/i18n_tm.py apply ar` (android 1520, ios 1457, desktop 1135 entries) and `python3 scripts/i18n_gen.py --check` (passes, exit 0). TOML still parses. Placeholders are unchanged in every edited entry: the apply/check scripts compare them against the English.

Where a sentence put a *contact* in front of «غير متصل», I rephrased it neutrally («لا اتصال لدى {first} الآن»). ## Bidi: risky strings and the code-side fix

The translations contain no direction marks, and they shouldn't. These are the patterns that will display wrongly with today's code, and the fix for each.

**Fix 1 (all platforms, fixes most of the 128): isolate every inserted argument.** Wrap each substituted value in FSI U+2068 … PDI U+2069 at insertion time: Android in the string-format helper (or `BidiFormatter.unicodeWrap` per argument), iOS in the `L10n` formatter (`"\u{2068}\(arg)\u{2069}"`), desktop in the `tr!`/format helper. Isolates are skipped when the paragraph direction is detected (UBA rule P2), so «{name} في {group}» with name “Ana” then takes RTL from the Arabic «في». The isolate also keeps “Ana Lee”, “Wi-Fi”, “.pdf”, “3:05” and “1280×720” whole and in order.
Affected: every entry that starts with a slot, e.g. `{name}. {status}. …` (`groups_chat_head_desc`, `conv_header_desc*`), `{name} (أنت)`, `{name} في {group}`, `{name} · تمت الإزالة`, `{name}، {what}…` (all screen-reader rows), `{size} · …` file lines, `{members} · …`, `{status} · …`, `{label}: {names}`, `{name}: {text}` (`group_preview_author`, `app_text`), `{inviter} · المالك {owner}`, `{value} · …` (desktop attachment lines), `{list} و {last}`, `{rest} و {last}`, `{value} و {last}`.

**Fix 2: base direction from the UI locale when nothing strong is left.** Strings made only of slots and symbols («{day} {time}», «{label}: {value}», «{members} · {hosts}», «{n} من {total}» with Latin digits) have no strong character once isolated. Lay out localized UI text with locale direction as the fallback: Compose `TextDirection.ContentOrRtl` (the default under an RTL `LayoutDirection`; make sure no screen forces `Ltr` or `Content`), Android Views `textDirection="locale"`, SwiftUI's default `.natural`, and on desktop set cosmic-text/iced's default paragraph direction from the locale.

**Fix 3: strings that start with a literal Latin word.** Isolation doesn't help here, because the brand or key name is part of the translation. I reordered the ones Arabic allows («تطبيق Tinline مفتوح المصدر», «للإلغاء: Ctrl E», «للرد: Enter · للرفض: Esc», «للإلغاء: Esc», «يريد {name} الانضمام…», «ليس {name} من جهات اتصالك»). Still starting with Latin: `app_name` “Tinline”, `call_hd` “HD”, `call_hd_paused` «HD متوقف مؤقتًا · اتصال ضعيف», `call_resolution_hd` «HD · {size}», `addcontact_tab_qr` “QR”, `call_route_bluetooth`, `link_linux`/`link_windows`, `profile_known_website_hint` “https://”, tray `tray_tinline` «Tinline - {status}». Proposed fix: `scripts/i18n_gen.py` prepends RLM U+200F to every string of an `rtl = true` language whose first strong character (ignoring placeholders) is not RTL, when it writes the platform files. The lead has to agree to this, because VALIDATION.md rule 7 says no marks unless agreed. Single-word labels such as “QR” or “HD” alone are harmless either way.

**Fix 4: numbers and percent.** Format `{count}`, `{percent}`, `{loss}`, `{rtt}`, sizes and durations with the locale's number formatter (Android `NumberFormat`/`String.format(locale,…)`, iOS `.formatted()`, desktop ICU4X or a digits-map per locale). Then «{percent}٪» shows ٤٥٪ in ar-EG/ar-SA and 45٪ in ar-MA/ar-DZ, consistently. Digits typed into translations do not follow the locale; see R5.

**Fix 5: lists.** `groups_msg_and`, `group_names_and`, desktop `group_and` and the comma-joined screen-reader parts: use the platform list formatter, as already proposed in RESTRUCTURE §9d. Arabic CLDR gives «أ، ب و ج» with the Arabic comma.

**Fixed in the translation:** `conv_no_app_opens` «ملفات .{ext}» displayed as “pdf.”, because the neutral dot attaches to the Arabic side. It now reads «ملفات {ext}».
